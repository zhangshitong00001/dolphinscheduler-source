## Project Overview

Apache DolphinScheduler (v3.1.10-SNAPSHOT) — a distributed, high-availability workflow scheduling platform with a visual DAG editor. Java 1.8 backend (Spring Boot 2.6.1), Vue 3 + TypeScript frontend, Maven build.

## Build & Test Commands

```bash
# Full build (Java backend + UI)
./mvnw clean install -Prelease

# Build with Zookeeper 3.4.x instead of default 3.8.0
./mvnw clean install -Prelease -Dzk-3.4

# Skip tests during build
./mvnw clean install -Prelease -DskipTests

# Run all tests for a specific module
./mvnw test -pl dolphinscheduler-service

# Run a single test class
./mvnw test -pl dolphinscheduler-service -Dtest=ProcessServiceImplTest

# Frontend dev server (cd dolphinscheduler-ui first)
pnpm install
pnpm dev

# Frontend lint
cd dolphinscheduler-ui && pnpm lint

# Python SDK lint
flake8 --config .flake8 dolphinscheduler-python/
```

Artifacts produced in `dolphinscheduler-dist/target/`:
- `apache-dolphinscheduler-{version}-bin.tar.gz` — binary distribution
- `apache-dolphinscheduler-{version}-src.tar.gz` — source distribution

## High-Level Architecture

DolphinScheduler is a **decentralized multi-master/multi-worker** system. Components discover each other via a registry (Zookeeper, MySQL, or Etcd) and communicate over Netty RPC.

### Core Runtime Components

| Component | Description | Key Classes |
|---|---|---|
| **Master** | Schedules workflows, manages DAG state machine, dispatches tasks to workers | `MasterServer`, `MasterSchedulerBootstrap`, `WorkflowExecuteRunnable` |
| **Worker** | Executes individual tasks, reports results back to master | `WorkerServer`, `WorkerManagerThread` |
| **API** | REST API server, Web UI backend | `ApiApplicationServer`, Controllers in `api/controller/` |
| **Alert** | Alert notification server | `AlertServer` |

### Request Flow (Workflow Execution)

1. User submits workflow via API → `Command` row inserted into DB
2. `MasterSchedulerBootstrap` polls `t_ds_command` table, creates `ProcessInstance`
3. `WorkflowExecuteRunnable` traverses DAG, submits ready tasks to `TaskPriorityQueue`
4. `TaskPriorityQueueConsumer` dispatches tasks to workers (Netty RPC, host selection via RoundRobin/Random/LowerWeight)
5. `WorkerManagerThread` executes the `TaskChannel` (runs actual shell/Spark/etc job)
6. Worker sends task result → Master `TaskExecuteResponseProcessor` → state machine advances
7. `WorkflowEventLooper` processes state transitions until DAG completes

### State Machine Architecture

The master uses an **event-driven state machine** for workflow and task state handling:
- `StateEvent` / `StateEventHandler` (abstract base)
- `WorkflowEventHandler` subclasses: start, submit, running, timeout, block, fail
- `TaskEventHandler` subclasses: dispatch, running, result, retry, timeout, reject
- `StateWheelExecuteThread` polls `WorkflowEventQueue` and dispatches to registered handlers

### Module Dependency Layering

```
API / Master / Worker (Spring Boot apps)
    └── dolphinscheduler-service (shared business logic)
        ├── dolphinscheduler-dao (MyBatis-Plus mappers + entities)
        ├── dolphinscheduler-remote (Netty RPC)
        └── dolphinscheduler-common (constants, enums, utilities)
```

### Plugin Architecture (SPI-based)

All extensible components use Java SPI with `PrioritySPIFactory`. Each plugin type has an API module defining the contract, and implementation modules loaded at runtime.

**Task Plugins** (`dolphinscheduler-task-plugin/`):
- SPI interface: `TaskChannelFactory` (extends `UiChannelFactory`, `PrioritySPI`)
- To add a task type: implement `TaskChannelFactory` + `AbstractTask`, add `META-INF/services` file
- ~33 task types: Shell, SQL, Spark, Flink, MR, Python, HTTP, SubProcess, Dependent, Conditions, Switch, DataX, Sqoop, SeaTunnel, Pigeon, Jupyter, MLflow, PyTorch, DVC, Kubernetes, EMR, SageMaker, OpenMLDB, Dinky, Chunjun, Zeppelin, Blocking, DataQuality, Procedure, HiveCli, Stream Flink

**Datasource Plugins** (`dolphinscheduler-datasource-plugin/`):
- SPI interface: `DataSourceChannelFactory`
- ~12 datasources: MySQL, PostgreSQL, Hive, Spark, ClickHouse, Oracle, SQLServer, DB2, Athena, Presto, Redshift

**Registry Plugins** (`dolphinscheduler-registry/`):
- SPI interface: `Registry` — provides service registration/discovery, distributed locks
- Implementations: Zookeeper, MySQL, Etcd

**Scheduler Plugins** (`dolphinscheduler-scheduler-plugin/`):
- SPI interface: `SchedulerApi` — CRUD for scheduled (cron-based) workflow triggers
- Implementation: Quartz

### Database Layer (MyBatis-Plus)

- **Entity classes**: `dolphinscheduler-dao/src/main/java/.../dao/entity/` — `ProcessDefinition`, `ProcessInstance`, `TaskInstance`, `TaskDefinition`, `Command`, `Schedule`, `Project`, `User`, `Tenant`, `DataSource`, etc.
- **Mapper interfaces**: `.../dao/mapper/` — extend MyBatis-Plus `BaseMapper<T>`, use `@Mapper` annotation
- **Repository wrappers** (optional): `.../dao/repository/` — e.g., `ProcessInstanceDao`, `ProcessDefinitionDao`

### Frontend (`dolphinscheduler-ui/`)

- **Framework**: Vue 3.2 + TypeScript + Vite 3 + Naive UI 2.30
- **State management**: Pinia (`src/store/`)
- **Routing**: Vue Router 4 (`src/router/`)
- **Service layer**: Axios-based API calls (`src/service/`)
- **Key views**: `views/projects/` (workflow CRUD, DAG editor), `views/datasource/`, `views/monitor/`, `views/security/`

### Python SDK (`dolphinscheduler-python/`)

Python client library for interacting with DolphinScheduler API, allowing workflow definition via code.

### Key Configuration Files

- `pom.xml` — root Maven config with all module definitions, dependency versions
- `dolphinscheduler-api/src/main/resources/application.yaml` — API server config
- `dolphinscheduler-master/src/main/resources/application.yaml` — Master server config
- `dolphinscheduler-worker/src/main/resources/application.yaml` — Worker server config
- `script/env/dolphinscheduler_env.sh` — environment variables for deployment
- `style/spotless_dolphinscheduler_formatter.xml` — Java code formatter config (Eclipse format)
- `.flake8` — Python lint config (max line length 110)

### Standalone Dev Server

`dolphinscheduler-standalone-server` packages API, Master, Worker, and Alert into a single JVM process for local development. Start via `script/dolphinscheduler-daemon.sh start standalone-server`.

## Coding Standards（编码规范）

### Naming
- **Components**: PascalCase (e.g., `WorkflowEditor`, `TaskCard`)
- **Regular variables**: camelCase (e.g., `userName`, `dataSourceList`)
- **File names**: Match the primary export (PascalCase for components, camelCase for stores/utilities)

### Error Handling
- Never swallow exceptions — always log the complete error with full stack trace (traceback).
- Use `@Slf4j` on Java classes for structured logging.

### Quality
- Must pass type checking and linting before commit.
- **Never use `any` type** in TypeScript — always define proper interfaces/types.
- Run `pnpm lint` before committing frontend changes.

### Style
- Follow the existing patterns in the codebase precisely. Do not invent new patterns.
- **Java**: Use Lombok annotations (`@Data`, `@Slf4j`, etc.). Follow existing patterns in each module.
- **Frontend**: Vue 3 Composition API with `<script setup lang="ts">`. Pinia stores use camelCase filenames.
- **Python**: Follow flake8 rules (max line 110, no D107).

### Commits
- Use `type: description` format (types: `feat`, `fix`, `refactor`, `test`, `docs`, `chore`).
